# key / 接口不稳定的成熟优化方案

> 评估日期 2026-11-06。基于当前代码实测，不是泛泛而谈。

## 一、现在到底怎么应对的

| 机制 | 现状 |
|---|---|
| 重试次数 | 临时故障 10 次，其它 2 次 |
| 退避 | 1.5s 起、指数、封顶 12s、带抖动，10 次共 **97 秒** |
| 错误分类 | 401/403 → 不重试；429/5xx → 按临时故障 |
| 失败可见 | 每次重试往群里发一条「在等接口恢复…」 |
| 换模型 | `decideRetry` 返回 `switchModel`，第 6 次起为 true |

## 二、实测出来的四个问题

### 问题 1：没有熔断，一个坏 key 打成 66 次请求

6 个成员的群，如果 key 彻底不可用：

```
每个 bot: 10 次重试，等 97s
总请求数: 66 次（首次 + 10 次重试）
总等待(累积): 584s
用户看到: 6 条"在等接口恢复"
```

**第 1 个 bot 撞 3 次就能确定这个 key 不通了**，但剩下 5 个还要各撞 11 次。
这是典型的**重试风暴**（retry storm）—— 上游已经挂了，我们还在加压。

### 问题 2：`switchModel` 是假的

```js
const hinted = retryHint({ ..., switchModel: decision.switchModel === true });
res = await this.run(roomId, bot.id, hinted + prompt, { groupTurn: true });
```

`switchModel` 只影响**往 prompt 里加一句话**：

> 「接口一直不稳定，可能要换模型了。…先把已经确认的事实和结论写下来」

然后 `this.run(roomId, bot.id, ...)` → `#ensureSession` 复用同一个 session，
session 是用 `bot.model` 建的 —— **模型根本没换**。

结果是很尴尬的状态：跟模型说"要换模型了"，但它自己就是那个不稳的模型。
模型可能因此提前收尾保存进度，而实际上什么也没换。

### 问题 3：一个组只有一把钥匙、一条路

```
ModelGroup = { baseUrl（单个）, apiKey（单个）, models[] }
```

key 限流了、被封了、中转挂了 —— 没有任何备选。用户能做的只有手动改配置。

### 问题 4：健康记录太粗，撑不起智能决策

```
{ ok: boolean, ms: number, error: string, at: number }
```

只有"上次成功/失败"，没有错误率、没有 P95 延迟、没有连续失败次数。
所以做不了"这个 key 最近 10 分钟 80% 失败，先别用它"这类判断。

## 三、方案（按性价比排序）

### P0 —— 熔断 + 重试预算（半天，收益最大）

**熔断器（circuit breaker）**，按模型组维度：

```
closed    —— 正常工作
  连续失败 N 次（含 429/5xx/网络错） → open
open      —— 一段时间内不再发请求，直接快速失败
  冷却 60s → half-open
half-open —— 放一个请求探路
  成功 → closed；失败 → 重新 open
```

效果对比：

| | 现在 | 加熔断 |
|---|---|---|
| 总请求数 | 66 | **3** |
| 用户看到 | 6 条"在等接口恢复" | **1 条"这个组的 key 不可用"** |
| 恢复判断 | 靠各 bot 各自重试撞 | 一次探路就知道 |

**重试预算（retry budget）**：整个**组**在 60s 窗口内最多 N 次重试，不是每个 bot 各 N 次。
这是 Google SRE 手册里的做法 —— 防止重试把系统压垮。

两个都是纯逻辑，能单独写测试，不动主流程结构。

### P1 —— 多 key / 多地址轮转（1~2 天，最直接的解药）

```diff
 ModelGroup = {
-  baseUrl: string,
-  apiKey: string,
+  endpoints: [
+    { baseUrl, apiKey, label },   // 主
+    { baseUrl, apiKey, label },   // 备
+  ],
   models: [...]
 }
```

失败自动切下一个，成功的那条标记为优先。
这是"key 不稳"最本质的解法：不稳就换一把，而不是硬等。

代价：数据模型要迁移（老配置自动包成单元素数组），设置界面要能加多行。

### P2 —— 健康评分升级（半天）

把布尔换成滑窗统计：

```
{ ok, ms, error, at,
  window: [{ ok, ms, at }, ...],   // 最近 N 次
  errRate, p95ms, consecutiveFails }
```

有了它才能做"这条通路最近 80% 失败，先降权"——现在只能做"上一次成功/失败"。

### P3 —— 对冲请求（不建议做主流程）

同时发两份、取先回来的。适合**只读探活**，不适合主流程 ——
成本翻倍，而且工具调用类请求重发会重复执行副作用。

---

## 四、建议的落地顺序

```
1. P0 熔断 + 重试预算     ← 先做这个，半天，风险低，收益立竿见影
2. 修 switchModel 的谎     ← 要么真换模型，要么把那句话删掉
3. P1 多 key 轮转          ← 治本，但要动数据模型和界面
4. P2 健康评分             ← 有了 P0/P1 之后才有意义
```

P0 不依赖任何数据模型改动，也不会让现有行为变差（最坏情况就是不加熔断）。

## 五、P0 的具体设计

### 熔断器状态

```js
CircuitBreaker {
  state: 'closed' | 'open' | 'halfOpen',
  fails: number,          // 连续失败次数
  openedAt: number,
  probeInFlight: boolean, // half-open 时防止并发探路
}
```

纯函数接口（便于测试，不碰定时器）：

```js
canRequest(cb, now)        -> boolean
recordSuccess(cb)          -> nextState
recordFailure(cb, now, {kind}) -> nextState
```

### 哪些失败算"电路故障"

| 类型 | 计入熔断 | 理由 |
|---|---|---|
| 429 限流 | ✅ | 上游在明确说"别来了" |
| 5xx / 网络错 | ✅ | 通路问题 |
| 401/403 | ✅（直接 open） | 凭证问题，重试无意义 —— 一次就够开 |
| 超时 | ✅ | 通路慢 |
| 用户终止 | ❌ | 不是故障 |
| 任务本身失败（模型说做不了） | ❌ | 不是通路问题 |

### 重试预算

```js
// 每个 groupId 一个滑窗
retryBudget = { groupId: { windowStart, used } }
// 60s 内最多 20 次重试
```

超预算时：不再逐个重试，而是**一次性**告诉负责人"这个组现在不稳，先别派活"。

## 六、不做什么（避免过度设计）

- **不做自动降级到别的模型组** —— 用户配的组有各自的用途和价格，
  自作主张换组可能在烧他没想到的钱。
- **不做请求重放幂等化** —— 工具调用（写文件、跑命令）重发会重复执行，
  这个问题不该靠"重试层"解决，应该在工具层做幂等键。当前没有真实需求。
- **不做指数退避到几分钟** —— 用户会以为卡死了。97 秒已经是体感上限。
