# Spec：让 bot 之间「像在对话」

状态：草案 · 待实现
影响范围：`server/src/dm.js`、`pi-runner.js`、`group-round.js`、`group-prompt.js`、`tools.js`、`app/lib/widgets/`
关联提交：当前 `main`（57c2a2b）之后

---

## 1. 问题

对比 Grok 与 pi-bot 的 bot 间协作截图，pi-bot 的状态消息读起来不像对话，原因有三层，彼此独立：

| # | 症状 | 根因 |
|---|---|---|
| P1 | 每条消息都是「在「X」接到活，开始处理：…」/「「X」那件事做完了：…」 | 回执文案是 **代码里拼的固定模板**，模型没有机会用自己的话说 |
| P2 | 6 条消息里 3 条是「接到活」，信息量为零 | 「我接到了」对用户不构成新信息，却占一条消息 |
| P3 | 弹窗把工单往来平铺成聊天气泡，读不出「谁在回应谁」 | 没有回复关系；每条是独立播报，气泡形态又在暗示对话 |
| P4 | bot 之间只有「派活→交货」，没有往返 | 缺少对等对话协议；`message_bot` 是单向 RPC |

其中 P1/P2/P3 是**表达层**问题，P4 是**结构**问题。前三个改完能解决「不像人话」，P4 才能解决「不像交流」。

---

## 2. 目标与非目标

### 目标

1. bot 之间的每条消息都能读出**谁在回应谁**。
2. 系统不再替模型生成仪式性文案。
3. 「接到活」这类零信息事件不再占用消息位。
4. bot 之间能做**有来有回**的对话（问 → 答 → 追问），而不只是派单。

### 非目标

- 不改变 TaskRun 状态机与验收逻辑。
- 不引入 bot 自主无限对话（必须有轮次上限）。
- 不改用户与 bot 的私聊交互方式。
- 不动消息存储 schema（复用现有 `refs` 字段）。

---

## 3. 设计

### 3.1 删除仪式性消息（P1 + P2）

**`server/src/dm.js`**

删除 `progressStartText()`。`shouldMirrorProgress()` 不再为 `phase: 'start'` 返回 true。

`pi-runner.js` 中两处 `#mirrorProgress({ phase: 'start' })` 调用直接移除（约 1804 行）。

`progressDoneText()` 保留但**降级为兜底**：只在模型输出为空时使用，且文案改为

```
（没有产出正文，任务 <ok|失败>）
```

正常路径不再套模板 —— 模型产出什么就发什么。

**不发的依据**：`memory-digest.js` 已经主动过滤「接到活/做完了」这类回执，说明系统自己判定它无信息量。既然不够格进摘要，也不该进用户会话。

### 3.2 消息带回复关系（P3）

现有 `Msg.refs` + `kind: 'ref'` 已支持引用，但 bot 间消息从不填写。

**改动**：`appendMessage` 在跨 bot 消息时写入 `meta.re`：

```js
meta: {
  via: 'message_bot' | 'mention' | 'dispatch',
  from: botId,
  re: sourceMessageId,        // 这条消息在回应谁
  attempt,                     // 保留
}
```

**渲染**：聊天气泡上方显示一行引用条（复用现有 ref 渲染），点击跳转到被引用的那条。

弹窗（「收到 N 条消息」）改成分组渲染：

- 按 `re` 链分组。有 `re` 的缩进显示在被回应者下方。
- 无 `re` 的（派单方）作为组首。
- 去掉气泡背景，改成左侧竖线 + 缩进表示层级。

### 3.3 对等对话协议（P4）

#### 3.3.1 现状

- `message_bot`：A 发 prompt → B 完整跑一轮 → 回结果。**单向，B 无法回问 A**。
- 群里 `@`：派活，被 @ 的人执行完发一条结论。**单向**。
- `planItem` 里同级 @ 会 `queue` 进 inbox，但没有「回应」语义。

#### 3.3.2 新增：`reply_bot` 工具

与 `message_bot` 的区别：

| | `message_bot` | `reply_bot`（新） |
|---|---|---|
| 语义 | 派活（要求对方执行） | 对话（提问 / 回答 / 澄清） |
| 对方行为 | 完整跑一轮再回 | 直接回一段话，不新建任务 |
| 可追问 | 否 | 是（受轮次上限约束） |
| 计入任务板 | 是 | 否 |
| 超时 | 300s | 60s |

```js
defineTool({
  name: 'reply_bot',
  label: '回一句话给某个 bot',
  description:
    '就近回一句话，用于澄清、确认、追问 —— 不是派活。\n' +
    '派活请用 @（群里）或 message_bot（跨部门）。\n' +
    '对方会直接回你一段话，不会开工。',
  parameters: Type.Object({
    botId: Type.String({ description: '对方 bot id' }),
    text: Type.String({ description: '要说的话', maxLength: 800 }),
    reMessageId: Type.Optional(Type.String({ description: '在回应哪条消息' })),
  }),
})
```

#### 3.3.3 往返上限

新增常量，按「一次对话」计数（不是单条消息）：

```js
export const PEER_DIALOG_MAX_TURNS = 4;   // A→B→A→B 最多 4 跳
export const PEER_DIALOG_TTL_MS = 120_000; // 超过 2 分钟不再延续
```

计数存在对话上下文里（`meta.dialogId` 串起来）。

超出上限时 `reply_bot` 返回失败，提示：

```
这次往返已经 4 轮了，继续聊下去会占用用户的注意力。
请直接给结论，或把需要决定的事上升给用户。
```

#### 3.3.4 触发条件

模型**什么时候**应该用 `reply_bot` 而不是自己闷头做？写进提示词：

```
★ 你看到同事的消息里有一处你无法自行判断（缺前提、前提矛盾、
  范围不清），先 reply_bot 问一句，不要凭猜继续做。
  问要具体：说清你卡在哪、需要它给什么。
```

#### 3.3.5 群内 @ 的回应语义

群里 A `@B` 派活，B 的回复自动带 `re = A 那条消息`。

若 B 需要 A 澄清，B 用 `reply_bot`（或直接 `@A` + 问句）。系统据此**不结束本轮**，把 A 重新入队。

`shouldStopRound` 已经支持「队列空但还有人在跑 → 不停」；这里补一条：**有未回答的 question 未终结时不停**。

---

## 4. 数据与兼容

- `meta.re` 是新字段，老消息没有 → 渲染层按「无引用」处理，无需迁移。
- `progressStartText` 删除后，历史消息里的旧文案仍能正常显示（只是不再新增）。
- `reply_bot` 是新增工具，不进 `MUTATING_TOOLS`（不改文件/不跑命令），进 `READONLY_ALLOW`。
- 不改变 `store` 的消息 schema，只是多写一个 `meta` 键。

## 5. 验收标准

### 自动化

| 编号 | 断言 |
|---|---|
| A1 | `shouldMirrorProgress({ phase:'start' })` 永不为 true |
| A2 | `progressStartText` 已从导出中移除 |
| A3 | 模型产出非空时，`mirrorProgress` 写入的正文与模型输出**逐字相同**（不套模板） |
| A4 | 跨 bot 消息的 `meta.re` 等于被回应消息 id |
| A5 | `reply_bot` 连续调用第 5 次返回失败，错误信息含轮次 |
| A6 | `reply_bot` 不创建 TaskRun、不写任务板 |
| A7 | 群里 B 回 `@A` 问句后，本轮不结束且 A 被重新入队 |

### 人工

| 编号 | 检查 |
|---|---|
| M1 | 派一个三 bot 协作任务，用户会话里**不出现**「接到活」 |
| M2 | 每条完成消息的正文第一句是实质结论，不是「「X」那件事做完了：」 |
| M3 | 弹窗能看出谁在回应谁（缩进 + 引用条） |
| M4 | 触发一次澄清：A 派活 → B 发现前提缺失 → B 问 → A 答 → B 继续 |
| M5 | 澄清往返超过 4 轮时，提示升级给用户而不是继续自循环 |

---

## 6. 实施顺序

分四批，每批可独立合并与验证：

| 批次 | 内容 | 风险 |
|---|---|---|
| **B1** | 删 `progressStartText`、`progressDoneText` 改兜底 | 低，纯删除 |
| **B2** | 跨 bot 消息写 `meta.re` + 渲染引用条 | 低，加法 |
| **B3** | `reply_bot` 工具 + 轮次上限 | 中，新增执行路径 |
| **B4** | 群内问句不结束本轮 + 弹窗改时间线 | 中，动轮次编排 |

B1 单独合并就能解决「不像人话」的主要观感。

## 7. 已定（用户裁决）

1. **界面对齐 Grok**：不用「任务时间线」，就按对话来做 —— 头像 + 名字 + 正文气泡，被回复的那条在上方显示引用块。bot 之间的往来在视觉上就是两个人在聊。
2. **`reply_bot` 跟随该 bot 自己选的模型**，不另设便宜模型。理由：bot 之间交流是为了拿到最佳答案，降级模型有丢失关键内容的风险，省这点钱不值。
3. **允许 bot 主动发起对话**（无人 @ 时自己找同事），**且不设往返轮次上限**。理由：任务没完成前的往返是必要的，硬性截断会让它们带着没解掉的问题收工。
