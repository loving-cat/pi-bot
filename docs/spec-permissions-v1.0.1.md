## 1. 结论与优先级

**P0：主 Bot 默认在用户当前普通登录身份下承担全机任务调度和 computer use，不要求所有 Bot 进入沙箱。全机任务视野不是无限数据读取许可，也不是管理员/root 身份，更不是跳过高风险确认。**

部门负责人获得用户指定项目的管理与普通 Git 权限；执行 Bot 获得具体任务的有限权限。授权由宿主权限服务执行，不能仅靠角色提示词约束。所有角色通过统一动作网关使用文件、命令、桌面、Git、网络和凭据能力。

**P0：权限粒度与真实执行能力一致。** 不能把“可运行任意宿主 shell”或“可控制普通登录桌面”包装成严格项目隔离。需要硬边界的执行任务采用受限工具、隔离进程或独立 OS 会话；做不到就拒绝该执行 Bot，交由主 Bot 在已获用户授权的范围内完成，不能偷偷扩大其权限。

**P1：Git 是开发闭环的必要能力。** 普通仓库、独立 clone、linked worktree 按信任关系选择；Git 可用和安全边界同时验收，不能以禁用 Git 交差。

**P2：** 在权限、取消与审计正确后，再优化截图增量、排队公平性、批量审批与性能。上下文预算由 Bot 集群专家团队复核，调度热路径与缓存策略由 pi-bot 算法优化组复核。

## 2. 产品目标与非目标

### 2.1 目标
- 用户自然语言交付端到端任务：主 Bot 理解目标、观察电脑、委派项目工作、汇总证据，必要时操作 GUI。
- 主 Bot 可以导航全机文件系统、切换应用，在当前用户真实可访问范围内完成任务；仅观察和处理当前任务需要的数据，不自动遍历全盘。
- 部门负责人对指定项目负责，能组织执行 Bot、处理 Git 分支与普通提交、汇总可验证产物。
- 用户始终可以接管、取消、收回授权；失败和权限不足明确报告，不伪报成功。
- Windows/macOS 均覆盖真实电脑操作与本地开发流程，平台差异必须显式显示。

### 2.2 非目标
- 不提供默认管理员/root；不绕过 UAC、TCC、目录授权、站点限制或用户拒绝。
- 不以同一 OS 用户下不同 Bot 的角色名提供硬隔离承诺。
- 不默认执行恶意样本、运行来源不明安装脚本，或让网页/仓库内容创建授权。
- 不把主 Bot 的所有权限自动下发给负责人或执行 Bot；不把同房间视为同一信任域。
- 不在本稿新增逆向 MCP 内置项；已有首批为零结论不因本次产品调整而自动改变。

## 3. 角色与组织

| 角色 | 职责与可见范围 | 默认能力设计 | 不允许默认获得 |
|---|---|---|---|
| 主 Bot | 接收用户目标、跨项目调度、电脑操作、审批呈现、结果汇总 | 当前任务所需的全机导航、受控宿主动作、桌面租约；在用户已授范围内执行 | 管理员身份、所有凭据、无限网络外传、危险操作免确认 |
| 部门负责人 | 指定项目计划、分解、评审、普通 Git 管理、失败升级 | 项目文件及 Git 普通操作；子授权只能取自身授权交集 | 跨项目文件、普通登录桌面任意控制、任意对外 push/merge |
| 执行 Bot | 单任务实现/分析/测试，交回证据 | 精确文件/命令/Git 子集；必要时独立隔离工作环境 | 自批权限、转授权限、修改策略、获取宿主任意 shell/GUI |
| 权限服务/动作代理 | 检查授权、执行动作、维护桌面租约与取消、记录审计 | 位于模型不可修改的宿主边界 | 接受模型声称“用户已批准”、依赖群消息作为授权 |

部门只是组织关系，不是 OS 安全边界。成员与角色变更不继承旧任务授权。同一 Bot 处理不同任务时分别绑定任务上下文，不混用授权或后台进程。

## 4. 典型端到端流程

### 4.1 开发与本地验证
1. 用户指定项目与目标；主 Bot 给出任务范围，识别现有授权和必须新增的确认。
2. 负责人选独立 clone / worktree / 普通分支，记录共享元数据与可接受的互相影响；若信任关系不满足则不用 worktree。
3. 执行 Bot 获得限时任务子授权，修改指定工作树、运行已允许的测试；不因测试需要自动获得任意宿主命令权限。
4. 负责人审查差异与测试证据，允许时创建普通提交。主 Bot 可用 GUI 在本地应用验证；桌面动作仍需逐次过网关。
5. 主 Bot 汇总实际完成、未验证和失败项。push/merge/删除等额外动作另走相应确认，不把“做完功能”当成发布授权。

### 4.2 电脑操作与对外动作
用户让主 Bot 整理资料并准备发送。主 Bot 获取桌面租约、观察相关应用、整理文件并生成消息预览。对外发送必须由用户确认具体收件人与内容；执行 Bot 仅交回资料，不取得邮件应用 GUI 控制权绕过发送边界。实际发送结果未确认时标“结果未知”，先对账，不重复发送。

### 4.3 不可信输入
执行 Bot 分析不可信仓库或附件。纯读取走受限读取器；构建、依赖安装、测试和样本执行均评估可执行风险。需要隔离时转到符合该任务威胁模型的沙箱/VM。隔离不可用则停止执行该步骤，继续可安全完成的静态分析；不得自动退回宿主运行。

## 5. Computer use 架构

### 5.1 组件与动作链
用户界面 → 主 Bot 任务编排 → 权限服务 → 桌面调度器 → Windows/macOS 动作代理 → 应用。

每次动作都携带任务、角色、实例、桌面会话和授权引用。动作代理独立校验当前授权、父授权链及撤销状态，不接受任意 Bot 直接调用低层输入。主 Bot 阅读并同意请求也不能替代执行入口的校验；任务、目标应用和有效期是必要条件，但只限制应用不构成完整资源隔离。截图/OCR、窗口标题、网页及文件内容都为不可信观察数据，不具有授权效果。

### 5.2 同一桌面调度
- 同一 OS 桌面会话只有一个能注入输入的租约；租约属于任务，不属于进程全局的“当前 Bot”。其他任务排队，允许独立的非桌面工作并行。
- 鼠标、键盘、焦点、剪贴板写入和影响窗口状态的动作纳入互斥区。观察按授权串行取一致快照，不把其他任务的窗口自动广播给所有成员。
- 租约有到期、心跳和世代号；旧持有者恢复后不能用旧租约继续输入。每次输入前检查取消状态、会话、目标窗口及观察是否过期。
- 高风险动作采用“观察—确认—重新校验目标—执行—核对结果”；不能跨很长队列复用旧坐标或旧确认。
- 用户显式接管立即吊销租约、丢弃尚未执行输入；检测到用户真实输入时暂停（检测可靠性与平台机制待核实）。按键释放、拖拽中断和超时恢复纳入验收。

### 5.3 执行 Bot 的 GUI 权限
普通登录桌面不能可靠提供“仅允许项目目录”的任意鼠标键盘控制：应用打开对话框、终端、地址栏都可能扩大实际能力。

因此默认不把该桌面的任意输入权限授给执行 Bot。它可提交受类型约束的 GUI 动作请求，由主 Bot 的动作代理在主 Bot 有效授权下执行并审计；主 Bot 不能把自己执行记成执行 Bot 已获权。对任意复杂应用无法可靠判断影响范围的请求，升级主 Bot/用户处理或使用独立 OS 会话。仅限制窗口名、进程名或模型承诺不构成安全边界。

**P0 代办不得借权**：代办请求默认必须同时满足原发起任务的有效授权和实际执行者的有效授权，不能只检查主 Bot 权限。超出原任务范围则拒绝本次请求或升级；主 Bot 必须依据真实用户目标独立判断是否承接，必要时向用户申请新增授权。承接后建立新的任务与授权关联，记录来源及扩大范围的依据，并重新通过执行入口校验；不能把下级请求本身当成用户目标或新增授权，也不能只换任务标识洗掉原始范围。

### 5.4 Win/mac 能力边界（设计需求，当前实现均待核实）
| 能力 | Windows | macOS | 共同失败策略 |
|---|---|---|---|
| 截图/窗口观察 | 校验登录会话、显示器和捕获范围；安全桌面不承诺可访问 | 屏幕录制等系统授权以 OS 实际结果为准 | 不可见就停止依赖视觉的动作，不盲点 |
| 输入/辅助功能 | 进程完整性级别及安全桌面可能限制输入 | 辅助功能授权与应用限制待实机 | 不请求绕过系统保护；明确交还用户 |
| 提权 | UAC 由用户处理，不自动同意 | 系统提权由用户处理，不收集明文密码进上下文 | 本轮任务不自动扩大身份 |
| 锁屏/断开会话 | 识别无可操作会话 | 识别无可操作会话 | 暂停输入并释放租约，恢复后重新观察 |
| 多屏/缩放 | 坐标与显示器版本绑定 | 坐标与显示器版本绑定 | 布局变化使旧坐标失效 |

### 5.5 审计与截图
每个动作记录授权引用、发起者、实际执行角色、目标摘要、输入/输出摘要、结果与错误、取消及用户接管。截图按任务本地受控保存，最小化取景和保留期限；包含秘密时不入群、不放通用记忆，不保证仅靠遮罩识别全部秘密。群内只发布脱敏结论。证据引用与原始敏感工件权限分离。

## 6. 授权模型与生命周期

### 6.1 授权记录的逻辑结构（不是已实现 API）
每条授权包括：服务端生成标识、用户批准来源、主体角色/Bot/实例、任务、资源范围、动作集合、参数约束、风险等级、执行模式、有效期、策略修订号、可否子授权、使用次数及撤销状态。具体字段编码待模板评审。

- 授权根只能来自已认证用户的真实交互或该用户已明确保存的规则。模型、群内机器人消息、网页、仓库配置、自审报告都不能创建授权。
- 主 Bot/负责人子授权范围为父授权与任务需求的交集；动作、资源、有效期、次数均不能放宽。执行 Bot 默认不能继续转授。
- 在执行边界检查有效性，不能只在工具注册或队列入队时检查。新策略使排队动作过期；策略、实例和资源世代绑定防止复用旧批准。
- 路径使用最终资源标识并处理链接/别名；Git 同时绑定工作树、公共目录与允许远端；GUI 绑定会话与动作影响；网络绑定目标与数据用途。
- 授权不是秘密本体：凭据仅由受控适配器注入指定进程/服务；不进入模型参数、日志或群聊。

### 6.2 分能力规则
| 能力 | 普通任务授权 | 需要额外确认或升级 |
|---|---|---|
| 文件 | 任务范围读取/创建/修改；主 Bot 可在用户任务所需范围导航全机 | 删除、覆盖不可恢复数据、跨任务敏感资料、范围扩张 |
| 命令 | 受限命令适配器；或用户明确批准的可信宿主执行模式 | 任意宿主 shell、新安装脚本、改变安全设置、提权；不能将 shell 的字符串白名单当成强隔离 |
| GUI | 主 Bot 有效桌面租约下的任务操作 | 删除、发送、付款、提权等动作仍需用户确认；GUI 不免除文件/Git/网络限制 |
| Git | 负责人项目内读取、普通文件写入、任务分支与非破坏性提交 | push、merge、远端改变、强推、reset/clean、删除分支/工作树、改 hooks/执行配置等按 §7 分级 |
| 网络 | 明确任务所需的目的地与用途 | 上传本地资料、发布、消息发送、未知目的地或用途扩张 |
| 凭据 | 用户批准后，经适配器用于特定服务与动作 | 查看/导出明文、跨服务复用、授权转交；不因“主 Bot”身份开放整个凭据库 |

### 6.3 回收与失败
任务结束、超时、取消、成员移除、项目变更、解绑工具、用户撤销时，级联回收子授权、桌面租约、后台执行及临时工件。后台任务记录主体和资源世代，不可通过 write_stdin 续接越过撤销。

取消请求先停止新动作，再尝试终止可归属进程；不可中断的系统调用或已提交外部动作不能承诺撤回。必须报告“取消中/部分完成/结果未知”，重新观察后对账，禁止自动重试付款、发送或提交等有副作用操作。

授权服务不可用或凭据适配器失败，拒绝相应动作；computer use 不作为后门。共享会话引用只传标识，不能凭标识推导权限。

## 7. Git 权限与工作区策略

### 7.1 操作分级（设计默认，仍受用户明确指令约束）
- G0 普通读取：status、diff、log 等由受控适配器执行，并检查外部 diff、textconv、分页器等执行配置风险；不能仅凭“只读命令名”认定无执行副作用。
- G1 项目普通开发：在授权任务分支修改、add、普通 commit，受项目授权覆盖；配置的 hooks、过滤器、签名程序等可触发执行，必须采用已评估策略，不自动信任仓库配置。
- G2 对外/集成：push、merge、rebase 共享分支、创建外部发布，默认提交具体仓库、远端、引用及差异摘要供用户确认；用户可另行明确授予窄范围长期规则，不预设已经存在。
- G3 破坏性/执行策略：force push、reset --hard、clean、删除分支或 worktree、改远端、改 hooks/可执行配置、跨项目操作须具体确认；不能伪装成普通文件写入或 GUI 点击绕过。

普通提交若需要 hooks/签名：要么使用已受控批准的执行链，要么采用用户接受的受限模式；不得静默关闭项目要求后声称提交流程正常。push 的网络许可不等于 push 授权，二者同时成立。

### 7.2 工作区选择
| 方案 | 适用条件 | 约束 |
|---|---|---|
| 同一工作树 | 串行任务，用户接受共同修改 | 写入租约；不让多个 Bot 并发改索引/工作文件 |
| linked worktree | 同项目、同信任域、明确接受共享 Git 元数据 | 独立索引不等于独立权限；记录并限制公共元数据，统一协调共享写操作 |
| 独立 clone | 不同信任域、执行不可信构建、需要元数据隔离 | 默认不使用共享可写对象库；alternates、硬链接、凭据与网络另审；仍非自动 OS 隔离 |

不用 worktree 作为所有项目的强制选项。若现有权限工具无法支持精细元数据授权，优先独立 clone 或受控 Git 代理，不能给整个主仓库无限 RW 后宣称隔离。

### 7.3 worktree 授权图与并发
解析并登记 `.git` 指针、gitdir、commondir、objects alternates、公共 config/hooks/refs/objects 与每工作树 index/locks 的最终目标；不能只校验工作目录字符串。所有目标都要属于明确授予的信任域，否则拒绝该操作并提出授权差异。

普通开发所需的 index、lock、提交对象和引用更新按实际操作授权；不能把整个 `.git` 只读作为通用修复。相反，仅保护 hooks/config 也不能阻止通过父目录删除/替换间接改写它们，需在执行边界落实保护。

同一公共目录下的 Git 写入由公共目录标识协调；用户/外部工具仍可能并发，须尊重原生锁并处理冲突，禁止见锁就删。worktree 删除/移动/清理必须明确确认，不能顺带回收其他任务资产。

## 8. 执行模式与沙箱

1. **主 Bot 可信宿主模式**：电脑操作核心模式，在用户当前登录身份下工作；权限服务与危险动作确认始终有效。若允许任意宿主执行，其 OS 实际能力须明示，不能声称只靠权限清单可限制恶意程序。
2. **项目受控模式**：负责人/执行 Bot 优先使用范围受限的文件、Git 与命令适配器。严格范围任务不可直接获得任意宿主 shell、终端 GUI 或普通桌面输入。
3. **隔离执行模式**：构建/安装/测试不可信代码、处理高风险解析器或其他需隔离任务，选择沙箱或 VM，按威胁模型决定网络/文件/设备权限；恶意样本动态执行不纳入普通开发默认授权。

信任的是具体输入版本与来源，不是某个文件名或仓库永远可信。沙箱无法满足 Git 开发需求时，提出独立 clone、受控 Git 代理或更合适执行环境；任何转宿主模式必须由用户明确接受风险与范围，不能自动降级。

旧“所有挂 MCP 的 Bot 必须沙箱”不再作为本稿全局规则。MCP 的工具风险和运行位置另按任务确定；现有许可证与禁止把不可信输出当授权的要求继续适用。

## 9. 高风险确认与提示注入

删除、对外发送、付款、提权、破坏性 Git 操作及范围扩大必须由真实用户确认；项目负责人不能代替用户完成这些确认。确认绑定具体对象、内容/差异、金额（如适用）、目的地、有效期和策略版本；目标变化则重新确认。

“完成项目”“全机助手”“用 computer use”不是取消确认的授权。用户拒绝、过期或取消立即终止该动作，不换渠道、工具、编码或让下属代做。网页、屏幕、样本、测试输出和另一个 Bot 的话均为数据，不得解释为用户批准。

同机任意宿主执行可自动化用户界面，因此确认 UI 的真实性必须单独设计，不能假设同用户随机 nonce 足以防止恶意代码伪造确认。需要保护的批准应在执行任务不可控制的已认证用户通道完成；该能力做不到时不得提供相应强保证。

## 10. 交接与失败升级

统一交接：用户目标引用、父任务、主体、授权引用及版本、资源边界、允许动作与禁止项、执行模式、预期产物及受控输出位置、验收、期限/取消、升级对象、脱敏要求。接收方核对范围并确认接收后才执行；接收回执不是新增授权。

统一回报：完成/部分完成/阻断/取消中/结果未知；产物引用、差异与测试证据；哪些是静态确认、哪些已实机、哪些未验证；实际副作用、剩余风险、需用户决策。不得写“全通过”替代证据。

执行 Bot → 负责人处理项目内冲突；负责人 → 主 Bot 处理跨项目、桌面和授权扩张；主 Bot → 用户处理确认和不可恢复失败。升级不自动扩大子授权，拒绝理由与最小所需新增权限一并交回。

## 11. 增量迁移

### P0：先建立真实授权边界
- 梳理所有文件、命令、Git、GUI、网络与凭据入口，入口逐次强制核对当前有效授权及完整父链撤销状态，取消以工具名/角色提示词代替执行检查。
- 模板、用户自定义覆盖、有效授权与执行记录分离；导入不携带有效授权，升级或覆盖不得扩权，新增能力默认未授权。这是首版 P0，不能等升级界面完善后再做。
- 引入任务授权、级联撤销、桌面单写租约、用户接管与取消；普通桌面输入默认仅主 Bot 使用。
- 保留现有隔离能力作为执行模式，不直接全局删除沙箱；无法提供范围隔离的入口显式拒绝或标为用户批准的宿主模式。
- 隔离旧规则与新策略版本，切换时停止/核对旧后台进程，不让旧批准迁移成更宽的新批准。已有实例缺少新字段时不默认为全机授权。
- 建立可验收最小闭环：主 Bot 观察/操作普通应用、负责人管理一个项目、执行 Bot 修改并测试、用户确认后按范围交付。

### P1：Git 开发完整性与平台实机
- 普通仓库、worktree、独立 clone 三种路径与元数据授权图；支持 status/diff/add/commit，确认后的 push/merge；hooks/签名策略明确。
- Win/mac 分别完成 computer use 与开发闭环；ACL/TCC/窗口/句柄差异以实际证据记录。
- 审计、崩溃恢复、授权对账、共享元数据并发与有限缓存；缓存不得替代必要的每次执行校验。

### P2：效率与扩展
- 公平排队、任务优先级、截图增量、输出分页与证据外置；不得缓存扩张授权。
- 完善模板权限差异预览、审计检索与恢复体验，扩展隔离模式；模板导入升级不扩权已在 P0 实施，不得延后。
- pi-bot 内置/随包组件执行宽松许可证准入并核对传递依赖及打包清单；外部工具调用按 §14 单独处理。

| 桌面调度 | 两任务排队，单任务持有输入租约 | 旧租约、租约超时、取消、用户接管后输入全部拒绝；不发生串打 | P0 |
| 分级委派 | 负责人下发限时任务，执行 Bot 交回证据；主 Bot 在明确授权下跨项目操作成功 | 子授权扩大资源/动作/期限失败；跨实例句柄与标识不能复用权限 | P0 |
| GUI 间接越权 | 主 Bot 在原任务及自身授权交集内代办；用户明确授权主 Bot 跨项目处理并建立新任务关联后成功 | 下级借主 Bot 代办越界读取被拒；不能借终端/文件对话框/浏览器上传越过权限；只换任务标识不能扩权 | P0 |

| 普通 Git | status/diff/add/commit，按策略运行 hooks/签名 | 不误判失败为成功；不静默更改 hooks/签名策略；失败不放宽隔离 | P1 |
| worktree | 解析目标后执行普通开发、处理 index/lock | 越界 .git/commondir/alternates 拒绝；不能读写其他实例；共享修改如实暴露 | P1 |

## 13. 模板、角色配置与首次使用

### 13.1 四层配置结构（逻辑合同，非当前接口）
| 层 | 必要信息 | 变更与权限规则 |
|---|---|---|
| 版本化角色默认值 | 模板标识/版本、roleId、上下级、职责、允许申请的能力、可委派上限、失败升级对象 | 只是可申请能力，不是有效授权；模板不得签发 grant |
| 用户自定义覆盖 | 对应模板版本、用户修改的职责/范围/偏好、冲突记录 | 保留用户修改；冲突需明示；覆盖值不得突破有效授权上限 |
| 运行期授权 | grantId、真实用户授权来源、父授权、主体、任务/项目、资源/动作、有效期、撤销条件、策略版本 | 服务端验证；导入导出不携带有效授权；新增能力默认未授权 |
| 执行记录 | 委派/接收回执、授权链引用、实际动作、结果、证据、取消与副作用 | 与配置分离；按任务访问；报告不能反向变成授权 |

文件、命令、GUI、Git、网络、凭据分别声明。凭据值不进模板；只有权限服务持有安全存储引用，给 Bot 的交接只提供“可请求使用某项凭据能力”的非秘密引用，不能据此导出凭据。

导入创建新实例/角色标识并重新授权；升级保留自定义覆盖，字段迁移不复制旧 grant。职责变化、资源扩大、工具新增、执行模式放宽都必须经过权限差异校验与必要的重新授权。无法判断是否扩权时，新增部分保持未授权，不取消既有安全功能。

### 13.2 首次授权流程
1. 展示主 Bot 的全机任务视野、当前普通用户身份，以及 computer use 的实际系统权限；说明危险动作确认不被取消。
2. 用户选择负责人项目和普通 Git 动作范围；明确远端操作、共享元数据、hooks/签名及凭据使用是否另需批准。
3. 为执行 Bot 分配任务级最小权限和执行模式；普通桌面通用键鼠权限不随角色继承。
4. 开始前汇总本次有效权限、到期/撤销条件、需逐次确认的动作和不能提供的硬隔离保证。OS 授权失败按实际结果报告，不自动切换更宽模式。
5. 完成后展示产物、实际测试边界及副作用，级联回收临时权限；用户可保留明确项目授权，但不能从“保留项目”推导长期对外发送或付款权限。

## 14. 工具链与许可证边界

### 14.1 computer use 能力选择
优先评估 Windows/macOS 系统原生输入、辅助功能、窗口和截图接口；这只是选择方向，具体 API 组合、兼容性、部署及许可义务均待核实，不在本稿捏造可用组件或完成状态。第三方封装必须检查源码、直接/传递依赖、打包产物与实际许可证。

每台交互桌面的宿主代理是执行串行化入口；操作系统权限受限时交还用户，不以浏览器、终端或执行 Bot 代替受阻能力。系统代理应处于任务代码不能随意修改的边界；同用户任意宿主执行无法提供该保护时，按 §8/§9 明示其威胁边界。

### 14.2 内置组件与用户已有工具分开
- **内置/随包分发**：遵守 Xiao 的 MIT/Apache/BSD 等宽松许可准入；核对锁文件、安装及打包清单、许可证义务和来源。未核实组件不得列为已选型内置依赖。
- **调用用户已有工具**：不因内置组件准入规则而禁止调用用户已安装的 Git，也不要求其许可证改为宽松许可。独立记录可执行来源、版本、使用范围，以及是否实际发生再分发；如捆绑安装器/复制二进制/随包交付，则重新进入内置分发审查。
- 调用已有工具不等于自动获得网络、凭据或任意命令权限。fetch/push 等网络操作还需相应目的地和凭据使用授权；fetch 不能因是“读取”就忽略其本地 refs/objects 写入及外部 helper 执行。
- 如引入替代 Git 库，功能、许可证与传递依赖均核实后才选型，不承诺其与 Git CLI、worktree、hooks、签名完全兼容。

### 14.3 Git 兼容性证据
Windows PowerShell 调 git.exe、Git Bash、macOS 各自列出普通仓库及 worktree 的实际状态，不能相互替代。操作成功至少核对进程退出状态与预期仓库状态；GUI 截图只证明当时界面，不能独立证明 Git 成功。

DS 关于 NUL 的归因仍属待核实线索，不作为“无法实现 Git”的设计结论，也不允许靠扩大设备/全机权限来免验。新增 worktree 的 shared metadata、索引和锁文件权限须与实际 Git 行为对照后验证。
