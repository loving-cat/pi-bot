# pi-bot 的分工模型

> 分工模型包含会话、调度和执行三层，以及部门策略、派活契约和可复用配置。

---

## 一、三层职责：谁管什么

现在这三层的边界还比较糊（很多判断写在 `pi-runner.js` 一个大文件里）。
明确成三层之后，每层的失败都只影响自己那层：

| 层 | 单位 | 负责 | 不负责 |
|---|---|---|---|
| **会话层** | 房间（私聊 / 部门） | 消息流、转发与来源、谁看得见什么 | 不决定谁来干活 |
| **调度层** | 部门 | 派活顺序、并发、打断、排队、预算、心跳 | 不碰模型和文件 |
| **执行层** | 房间 × bot 的会话 | 工具调用、上下文、产物落盘 | 不管别人死活 |

**已实现**：调度层（@ 派活、全员并发、上级可打断、同级投递、心跳看门狗、预算）
**要补**：把"策略判断"从执行层抽出来 —— 见下面第三节。

## 二、部门的"规矩"（policy）

一个部门不只是"一群人"，它应该带着一套**可配置的规矩**。
现在只有预算（轮次 / 时长），缺的是**行为约束**。

```
部门规矩
├─ 危险动作：允许 / 需批准 / 禁止
│   删除文件、改系统配置、装东西、访问网络…
├─ 交付标准：必须自验（跑测试/自检），必须附证据（命令输出/截图）
├─ 谁能打断谁：上级可打断 ✓ 同级投递 ✓ （已有）
└─ 预算：来回轮数 / 单轮时长 / 每条消息最多触发几次（已有）
```

**为什么值得做**：现在 bot 有 `bash`/`write`，出事只能靠系统提示里那句"要先问"。
规矩放到**部门**这一层之后：不同部门可以要不同的严格程度（研究部门宽松、生产部门严），
而且它是**可审计的**（看得见当前是什么规矩）。

**触发时用什么问**：复用已有的**询问卡片**（`ask_user` 那套 UI）——
不要另造一个"审批弹窗"。一张卡、几个选项（允许这一次 / 这个会话内都允许 / 拒绝），
用户在手机上点一下就过。

## 三、派活契约：工作说明书 + 验收标准

已经落地的（从派活失败的经验来的）：

- 传的是**工作说明书**，不是转述用户那句话
- **要做的事 + 要交回什么** 必须写清
- 超过上限**退回，不截断**（截断会静默削掉约束）

**验收标准**：派活时可以带明确的验收条件（写成一句话，比如"跑通 `node tests/unit.mjs`"）。
带验收标准的活，交回来时会**自动核对**（让交活的人把证据贴出来），
而不是让组长自己判断"这算做完了吗"。

## 四、部门模板：一次配好，反复开张

现在建部门是"一句话让主控现凑人"。凑出来的班子**每次都不同**，
而且配好的部门（人设 / 技能 / 模型 / 规矩）**没法重复用**。

**部门模板** = 一份可保存的配置

```
模板包含：部门名、几个人、每人（名字/人设/技能/模型）、部门规矩
用法：新建部门时可以"照某个模板开"；现有部门也能"存成模板"
```

**已有的基础**：造开发类 bot 会自动挂工程基线（`coding-baseline.js`）——
模板是它的推广：把"一整套人 + 规矩"也变成可复用的。

## 五、消息的"定稿"状态（先不急，记着）

值得记一笔：消息除了 `streaming / done / error`，还可以有**已定稿**——
用户确认过的结论、或组长给出的最终答复。

**好处**：上下文压缩时可以优先保留定稿的消息；用户回看时一眼能找到结论。
**代价**：要多一套状态和交互。**现在不做**，等有真实需求再说。

## 六、运行边界

| 不采用的机制 | 技术原因 |
|---|---|
| "通话"隐喻（接听/挂断/静音） | 交互以群聊和部门任务为单位 |
| Realtime 事件协议 | 执行层使用 pi 会话，无浏览器实时语音事件流 |
| 云端 agent + 看屏幕 | agent 在用户本机执行，数据与权限按本机边界管理 |

---

## 落地顺序（建议）

1. **部门规矩**（第二节）—— 收益最大：bot 能干活但不会拆家
2. **派活的验收标准**（第三节）—— 小改动，直接减少"交回来的活没法验收"
3. **部门模板**（第四节）—— 让好班子可复用

每一步都能独立上线，也都能单独回退。
