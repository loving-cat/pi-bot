# Agent 分工模型

本文说明会话、调度与执行的职责边界，以及策略、派活和部门模板的实现范围。

## 一、三层职责

| 层 | 单位 | 职责 | 主要模块 |
|---|---|---|---|
| **会话层** | 房间（私聊 / 部门） | 消息流、转发来源、消息可见性与游标 | `store.js`、`group-prompt.js` |
| **调度层** | 部门轮次 | 派活顺序、并发、打断、排队、预算与收尾 | `group-round.js`、`pi-runner.js`、`watchdog.js` |
| **执行层** | 房间 × bot 的会话 | 模型调用、工具执行、上下文与产物 | `session-factory.js`、`session-pool.js`、`artifact-watch.js` |

调度纯函数返回跳过、派发、排队或打断等决策，`pi-runner.js` 负责执行副作用。
每个房间与 bot 的组合持有独立会话；任务依赖通过共享消息和后续派发传递。

## 二、行为策略（policy）

当前策略由 `store.policy()` 统一提供，执行点位于 `policy-hook.js`。
设置中的部门规矩是统一策略，尚未按单个部门分别存储。

| 配置 | 判定规则 | 执行位置 |
|---|---|---|
| `dangerous` | `allow` 正常执行；`ask` 等待用户审批；`deny` 限制写入和命令工具 | `store.js` 的 `toolsForPolicy()`、`policy-hook.js` |
| `denyCommands` | 拒绝匹配的命令 | `shell-policy.js` |
| `allowCommands` | 非空时只允许匹配的命令 | `shell-policy.js` |
| `requireProof` | 在提示词中要求提交命令输出、文件路径或测试结果 | `system-prompt.js` |

命令匹配先进行归一化与解析，支持整条通配和 `exe:args` 规则。
可审批操作使用消息内卡片收集用户决定，审批记录与执行输入关联。
配置 `denyCommands` 时，命令策略会拒绝无法静态解析的命令。
当前 `ask` 模式的已有批准或会话授权可能先于命令规则检查返回，审批与命令规则不能视为独立沙箱。

**取舍**：执行期策略能集中约束工具调用；提示词中的交付要求只影响模型行为，
不能替代程序化验收。按部门分别配置策略仍需要独立的数据模型与合并规则。

## 三、派活契约

派活说明应包含任务目标、交付物、验收标准，以及约束和需要确认的环节。
`message_bot` 的任务正文上限由 `MAX_TASK_CHARS` 定义（4000 字符），超长直接退回，避免截断约束。
跨部门派发使用 `dispatch_to_department`，由负责人继续拆分任务。

验收标准目前作为任务正文传递，例如“通过 `node tests/unit.mjs`”。
交付证据由执行者提供；独立、结构化的自动验收仍是后续扩展方向。

**收益**：任务输入更完整，交付结果更容易核对。
**成本**：任务说明占用上下文；自动验收还需定义证据格式、失败处理和重试预算。

## 四、部门模板

模板用于复用部门配置，相关存储与应用接口位于 `store.js`。

- 模板保存名称、主题、负责人和成员配置。
- 成员配置包含名字、头像、简介、人设、模型、思考强度与技能。
- 可以从现有部门保存模板，再按模板创建部门；同名成员按创建规则复用。
- 模板不包含消息和执行会话，也不单独保存行为策略。

**收益**：减少重复配置，保持成员分工一致。
**边界**：复用成员可能共享其后续配置变动；模板不是历史会话快照。

## 五、消息定稿状态（规划）

可在 `streaming / done / error` 之外增加定稿标记，用于用户确认的结论或负责人最终答复。

**收益**：上下文压缩时可优先保留定稿内容，回看时更容易定位结论。
**成本**：需要新增状态、撤回规则和界面交互；当前未实现。

## 六、能力边界与后续方向

当前交互以群聊和部门为单位，执行会话在用户主机运行，不包含通话状态机、浏览器实时语音协议
或云端远程桌面执行。这些能力需要额外的会话生命周期、权限和数据传输设计。

后续扩展可按以下顺序独立推进：

1. 按部门配置策略，并明确与统一策略的合并优先级。
2. 为派活增加结构化验收标准和证据校验。
3. 扩展模板配置范围，并明确成员复用和配置更新的语义。

各项应独立定义数据迁移、测试与回退边界。
